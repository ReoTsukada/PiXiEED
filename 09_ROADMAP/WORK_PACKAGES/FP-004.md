## Objective

Build the first durable reference implementation of the FP-004 contract. A command becomes a
trusted canonical Event only after current server context and aggregate state are revalidated and
one durable transaction commits the state change, Event, Outbox row, and idempotency record. The
implementation is isolated and production-equivalent only; it must not replace WP-095 or connect
to production.

## Prerequisites and canonical inputs

- FP-003AA has an independent approval record, including authenticated server context and the
  three blocking checks: concurrent double-consume, membership revocation, and malformed Ledger
  success.
- Read `docs/contracts/FP-004-DURABLE-EVENT.md` as the authoritative behavioral contract and use
  the FP-001 AuthorizationProofV1 / FP-003 financial contracts without redefining them.
- Use the existing Core identity vocabulary: tenant, aggregate type/id, revision, schema version,
  provider name/id, idempotency key, causation id, correlation id, and canonical result hash.
- Test adapters must include an in-memory adapter for fast unit tests and a restartable,
  transaction-shaped production-equivalent adapter. The former is never evidence of durability.

## Deliverables

- `pixiedraw2/src/fp-004/**`: typed Event, Inbox, Outbox, idempotency, transaction, lease/fencing,
  retry/DLQ, replay, and provider-identity implementation with no DOM, Canvas, product UI, or
  production SDK dependency.
- A versioned durable record model for canonical state, Event, Outbox, Inbox, idempotency, gap,
  lease, consumer result, and DLQ records. Every record is tenant/resource bound and privacy-safe.
- Conformance and failure-injection tests covering every matrix row below, restart recovery, and

## Non-scope

FP-004 does not implement product UI, raw image/audio/game/package storage, payment execution,
provider credentials, Search/Notification/Finance business rules, schema migration, FP-005 input
limits/storage policy, FP-007 build reproducibility, current-route integration, or production
DB/Storage/queue changes. High-frequency Draw2 strokes remain local command traffic and are not
converted into durable global Events here.

## Invariants

1. `state + canonical Event + Outbox row + idempotency result` commit together or none commit.
2. Event identity, aggregate version, tenant/resource binding, schema version, and result hash are
   immutable after commit. A stale version never rolls state backward.
3. `(providerName, providerEventId)` is unique. Same identity plus same payload hash is a duplicate;
   same identity with a different hash, tenant, type, or mapping is `IDEMPOTENCY_CONFLICT`.
4. Idempotency is scoped to operation and tenant/resource. Same key/request hash returns the prior
   canonical result; same key/different hash mutates nothing.
5. Ordering is per `(tenantId, aggregateType, aggregateId)`: expected next version advances,
   lower version is stale/duplicate, higher version is a durable gap, and conflict is quarantined.
6. Only the lease owner with the current fencing token may acknowledge, complete, retry, DLQ, or
   cause a provider side effect. FP-004 claims at-least-once plus deduplication, never exactly-once.
7. Replay has `replayRunId`, consumer scope, and `sideEffectMode=NONE`; it may rebuild projections
   but cannot send, charge, refund, publish, mutate Ledger, or change canonical state.
8. Success without a committed transaction id, Event identity/version, required durable record,
   current AuthorizationProof, or validated provider identity is rejected as malformed success.

## Attack and failure matrix

| Fixture / injection | Required assertion | Evidence |
|---|---|---|
| Same command concurrently submitted | One commit, Event, Outbox, and canonical result; loser receives duplicate/conflict | `FP004-EVT-001` |
| Same provider id retried | Same hash is acknowledged once; different hash/tenant/type is quarantined | `FP004-EVT-002` |
| Missing/forged provider id or actor | Reject before state mutation | `FP004-EVT-002`, `FP004-SEC-001` |
| Crash before transaction / after state write / before commit | All-or-none durable state/Event/Outbox/Inbox outcome | `FP004-EVT-001`, `FP004-RECOVERY-001` |
| Crash after commit before response | Retry returns original result and never creates a second mutation | `FP004-EVT-001`, `FP004-RECOVERY-001` |
| Two Inbox workers, lease expiry, stale fencing token | One winner; expired/stale worker cannot ack or side-effect | `FP004-INBOX-001`, `FP004-RECOVERY-001` |
| Lower, higher, and conflicting aggregate version | Stale ignored, gap held durably, conflict quarantined | `FP004-ORDER-001` |
| Retryable, poison, non-retryable failure | Bounded backoff; independent consumer DLQ; no silent drop or infinite retry | `FP004-RECOVERY-001` |
| Replay of Finance/Notification/Search | Projection only; zero email/push/provider/financial mutation | `FP004-REPLAY-001` |
| Revoked membership or stale AuthorizationProof at commit/side-effect | Second server resolution denies and leaves state unchanged | `FP004-SEC-001` |
| Provider returns `{ok:true}` or unknown/inconsistent schema | Reject unless transaction id, identity, hash, and durable records validate | `FP004-EVT-002` |
| Malformed, cyclic, oversized, private, or cross-tenant envelope | Fail closed without leaking payload or creating gap/projection | `FP004-SEC-001` |

## Performance, security, privacy, and compatibility

- Measure transaction, Inbox, Outbox, retry, and replay latency separately at 1/10/100/1000-event
  fixtures; record p50/p95, queue depth, mounted records, and memory. Do not claim product or
  production SLOs from these fixtures.
- Reject JWTs, cookies, email, secrets, payment details, raw media, full project bodies, and
  credentials in Event/Inbox/Outbox/DLQ fields, logs, and error messages. Store only hashes,
  typed references, and bounded diagnostics.
- Use explicit schema versions and adapter capability checks. Unknown versions, unsupported
  capability, provider mismatch, and legacy WP-095 in-memory assumptions fail closed.
- Compatibility is contract-level only: existing WP-095 concepts may be adapted through a named
  adapter, but current PiXiSYNC, Market, PXD, routes, projects, assets, and purchased data are
  not changed or claimed compatible.
