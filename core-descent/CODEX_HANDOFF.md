## 2. 利用者が求めているゲーム

主人公1人を手動で動かし、武器による照準と攻撃を自動で行う、リアルタイムのファンタジーRPGです。サバイバー型の生存と無限階層の探索に、数字パズルとコアのビルド構築を組み合わせます。

- 職業で遊び方を固定せず、武器核と共通コアの組み合わせで変化させる。
- 初期から数字0〜9の10種類の武器核を使える。武器を変えても数字パズルを解く楽しさを残す。
- 組み合わせ次第で非常に強いビルドを作れる余地を残す。数字の配置と継承経路そのものが強さに影響する。
- 草原・砂漠・火山・毒沼・雪原という統一されたファンタジー世界。主人公、敵、武器、地形も同じ方向で作る。
- 32×32を基本とする2Dスプライトを多層に重ね、奥行きのある画面にする。探索して景色を見ることも楽しめる品質を目指す。
- ランダムな部屋の組み合わせでマップを作る。主人公の周囲から徐々に暗くなり、未探索の領域を隠す。
- 下の階へ進むか、帰還して戦利品を確保するかを選ぶ。コア以外にお金、素材、装備、消耗品も得る。
- 固有の敵に限定した素材・コア・装備、フィールドごとのボス、異なる移動と攻撃パターンで戦術を作る。
- PvPは採用せず、クリア階層と無限ボスへの総ダメージを競う方向。
- 将来の市場は全アイテムを取引対象とし、即決購入にも対応させたいという要望がある。オンライン市場自体は未実装。

初期案にあった複数キャラクター編成は、主人公1人とパワーコアの構成へ更新済みです。初期の射撃固定、PvP、旧バージョンの武器数値を現行仕様として復活させないでください。

## 4. 数字・コア・セーブの重要な条件

### 数字パズルと効果の継承

1. アイテムの数字0〜9は取得時に確定し、装着・戦闘・帰還・取引で変更しない。
2. 上の数字は直下2個の和の一の位。同じ段に同じ数字を重複させない。
3. 各コアの出力は「左下の出力＋右下の出力＋自身の効果」。同じ下位コアから複数経路で伝わる効果も加算する。
4. 最上段は武器核。保存上の種別名は `emitter`。その固定数字が武器種を決める。直下2枠に固定の役割を割り当てない。
5. 通常モードで武器を交換しても、その数字を成立させる配置が必要。盤面の自動完成は実験室に限定する。
6. 全32種のコアを全10武器で使う。武器や職業によるコア制限を追加しない。

9段の中央から頂点までは70経路、端は1経路になるなど、配置による重複継承は意図した仕様です。通常の効果を集合へ変換して重複排除すると、ビルドの意味が変わります。

### レア度・個体値・増幅

コモン、アンコモン、レア、エピック、レジェンダリーで数値が変わり、同レア度でも取得時に95〜105%の個体差が付きます。装着や帰還で再抽選しません。

増幅コアは、**直接つながる上側コア自身の数値**を強化します。継承済みの合計値全体を再増幅したり、経路数を増幅倍率の指数にしたりしません。詳しくは [レア度・増幅仕様](docs/RARITY_AMPLIFIERS.md) を参照してください。

装備補正はコア合成後の最終補正です。コアの経路による増幅へ含めません。特殊効果の小数を黙って切り捨てず、計算・画面・テストを整合させます。

### 所持品と記録

| データ | 現行の識別子 |
|---|---|
| 所持品の保存キー | `core-descent-v4` |
| 記録ルール | `0.9.0` |
| チャレンジID | `fantasy-magic-01` |
| 自己記録の保存キー | `core-descent-records-v9` |

既存アイテムのID・数字・レア度・個体値・編成を維持し、移行を繰り返しても重複や再抽選を起こさないようにします。旧記録のキーを削除せず、異なるルール版・チャレンジ・通常と実験室を混ぜません。到達階層とクリア済み階層は別です。

今回得た戦利品は帰還して初めて確保されます。死亡・放棄で失うのは未確保の荷物で、出発前の資産は保護します。使用した消耗品は使用済みです。コアだけでなく `bankRun` の `cargo` も検証して一括確定させます。

ブラウザーのローカル保存はサーバーが検証した競技記録ではありません。公開サイトとローカルプレビューの保存領域も別です。

## 5. 武器と二系統の魔法

| 数字 | 武器 | 攻撃条件 |
|---:|---|---|
| 0 | 剣 | 移動中も攻撃 |
| 1 | ダガー | 移動中も攻撃 |
| 2 | 大剣 | 0.18秒の静止準備。基礎威力90 |
| 3 | 槍 | 移動中も攻撃 |
| 4 | 斧 | 移動中も攻撃 |
| 5 | 槌 | 0.28秒の静止準備。基礎威力88 |
| 6 | 弓 | 移動中も攻撃 |
| 7 | チャクラム | 移動中も攻撃 |
| 8 | 星火の杖 | 0.35秒の静止詠唱。高威力の魔力球と着弾爆発 |
| 9 | 古代の魔導書 | 移動詠唱。3連追尾魔弾 |

| 数値 | 杖 | 魔導書 |
|---|---:|---:|
| 基礎威力 | 45 | 1発12 |
| 攻撃速度 | 1.35回/秒 | 1.10斉射/秒、1斉射3発 |
| 射程 | 350px | 300px |
| 弾速 | 245px/秒 | 300px/秒 |
| 固有効果 | 初回命中で半径55pxの別の敵へ70%爆発 | 弾間隔0.1秒、追尾1.2rad/秒 |
| 補正前の直撃参考DPS | 60.75 | 39.60（3発とも命中） |

参考DPSは継続命中時の武器基礎値です。会心、コア、装備、レベル、範囲巻き込み、移動、初回の準備を含みません。武器核自身にも威力補正があるため、画面の最終値とは異なります。杖の爆発は直撃相手へ二重加算しません。

静止武器の共通ルールは次のとおりです。

- 移動入力で準備をリセットする。壁に向かって入力している場合も同様。
- 発射後に移動を固定しない。発射済みの弾は移動しても飛び続ける。
- 静止を続けている間は通常の攻撃間隔で攻撃する。毎発、準備時間を余分に加算しない。
- 攻撃速度はクールダウンを変え、準備時間は短縮しない。
- 移動中もクールダウンは進む。発動しなかった通常攻撃の回数を貯めない。
- 回復から発生する追加攻撃にも同じ準備条件を適用する。
- 通常探索、階層ボス、無限ボスで条件を揃える。

`AGENTS.md` と古い資料にある v0.8の「移動攻撃8武器」は履歴です。現行は**移動7・静止3**です。数値の正本は `src/weapons.mjs`、説明は [RELEASE_V09.md](docs/RELEASE_V09.md) です。

## 6. フィールド・描画

| 初回の階層 | フィールド | ボス |
|---|---|---|
| 1〜5 | 翠風の草原 | 草原の古老樹 |
| 6〜10 | 砂眠りの遺跡 | 砂丘の大蠍 |
| 11〜15 | 熾火の火山 | 熾火の古竜 |
| 16〜20 | 瘴気の湿原 | 瘴気のヒュドラ |
| 21〜25 | 白霜の雪原 | 白霜の巨人 |

5階ずつの帯を25階周期で繰り返し、絶対階層で難易度を上げます。5の倍数の階はボス撃破も進行条件です。通常探索は1階から始まり、任意フィールド・ボス階からの体験は実験室です。

描画はコードから生成するオリジナルのドット原画を使います。人物・敵・武器の原画基準は32×32で、高さ別の水平層を積み重ねます。ボスの表示倍率は原画サイズと分けています。

床のまとまり、石畳、草木、遺跡模様、鉱脈、茸、雪や氷などを部屋単位で配置します。環境粒子は草原の花粉、砂塵、火の粉、胞子、雪で変えます。最大描画数は高品質36・軽量12・演出軽減時0です。

景観は表示だけを担当します。装飾で歩ける床を壁へ変えたり、AI・衝突・ダメージ・戦闘乱数・戦利品を変えたりしません。装飾の決定的な生成処理はゲーム用乱数列から独立させ、原画・地形・部屋景観をキャッシュします。

霧は論理的な視界と既探索を維持しながら、距離に応じて滑らかに暗くします。未探索の敵・戦利品・出口・装飾や光源を先に表示せず、壁の遮蔽を保ちます。危険床と攻撃予告は装飾の上に描き、読みやすさを優先します。

独自ビルドは指定順にモジュールを束ねます。現状は名前付きimportとトップレベルの `export const` / `let` / `function` / `class` を想定しています。新しいモジュールや別形式のimport/exportを足す場合は `tools/build.mjs` の対応も確認してください。ランタイムの追加依存はありません。

## 8. 起動・検証・配信

### ゲーム単体

Node.js 22以上を使用します。取得済みリポジトリのルートから実行してください。

```sh
cd core-descent
npm run build
npm test
npm run balance
npm start
```

ローカルURLは `http://localhost:4173/`。サーバーは `dist/index.html` を配信するため、起動前のビルドが必要です。ポート競合時は環境に合う方法で `PORT` を設定してください。ゲーム単体のビルドとテストはNode.js組み込み機能を使います。

`npm run balance` の固定命中による理論計算と、移動・射程・壁・敵AIを含む実戦DPSは区別してください。

### PiXiEED全体

全体の配信を変更する場合は、リポジトリルートの依存関係とビルドも確認します。以下はmacOS/Linuxの例です。Windowsではリポジトリ外の出力先へ置き換えてください。

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm run build -- --output /tmp/pixieed-core-descent-preview
```

ゲームの公開成果物は `core-descent/index.html` のみです。`src/`、`tests/`、開発資料、QAページ、スクリーンショット、ローカル配信設定をゲーム公開ディレクトリへ丸ごと配信しません。QA画像は公開サイトにもLibraryにもアップロードしないという利用者の希望を継続します。

`.github/workflows/pages.yml` が `main` 更新時の公開ビルドとGitHub Pages配信を行います。他のPiXiEEDツールや配信設定は、今回のゲーム作業に必要な範囲で扱ってください。

### v0.9で完了済みの確認

これはv0.9リリース時の実績です。新しい環境で実行した結果とは分けて扱います。

- 自動テスト **253 / 253成功**。
- ゲーム単体ビルド、数値レポート、PiXiEED全体の公開ビルドが成功。
- ローカルの実ブラウザーで5フィールド、通常探索、実験室、杖の停止詠唱、魔導書の移動攻撃、無限ボス、v0.9記録保存を確認。
- デスクトップと390×844 / 844×390の縦横画面、人物・敵・ボス・地形の原画を確認。
- 上記GitHub Actionsでbuild / deployの成功を確認。

実機スマートフォンのタッチ操作と広い端末での性能は未検証です。前セッションでは公開URLへの直接ブラウザー確認がアクセス権限で拒否されたため、公開サイトの実画面は確認していません。これはそのセッションの検証範囲であり、サイト障害を意味しません。新しい環境で許可される確認範囲を使い、未確認部分を明記してください。

コード変更後は `npm run build` と `npm test`、数値変更時は `npm run balance` を実行します。UI変更時はデスクトップ・モバイル幅の実ブラウザーでも確認します。資料だけの変更にゲーム全試験の再実行を必須とはしません。

## 9. 次のセッションで最初に行うこと

1. 現在のブランチ、HEAD、未コミット差分、利用可能な実行環境を確認する。既存の作業を上書きしない。
2. `AGENTS.md`、本資料、`README.md`、`docs/RELEASE_V09.md` を読み、ソースと照合する。継続仕様はv0.8・v0.7資料も参照する。
3. ゲームをビルド、テスト、ローカル起動する。失敗した場合は原因と必要な修正を特定する。
4. 通常探索と実験室、杖の停止詠唱と魔導書の移動攻撃、現在の保存・記録バージョンを確認する。
5. 引き継げた内容、起動先、実際に確認した問題、未確認の範囲を日本語で報告する。

その後は利用者の次の開発指示に沿って進めます。引き継ぎだけを根拠に、オンラインDBや実市場の導入、全体のエンジン置換、数値バランスの全面変更を開始しません。実機での操作・性能とオンライン基盤は今後の検討対象です。
