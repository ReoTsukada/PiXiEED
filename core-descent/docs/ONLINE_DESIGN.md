# 本番オンライン設計 — 未実装の契約

この文書は実装計画。v0.2のブラウザーセーブやAuctionBookは安全なオンライン取引サービスではない。`backend/schema.sql` も未適用・未DB検証の設計案。

## 信頼境界

ブラウザーは描画、操作入力、編成案の編集を担当。サーバーがプレイヤーID、所持品、コア定義のバージョン、編成の合法性、戦闘結果、戦利品、帰還、残高、出品を確定する。

クライアントから「100階を攻略した」「このコアを拾った」「DPSが1万だった」という結果を受け取って信用しない。seedだけ渡して結果を自己申告させる方式も不可。ローカルセーブをオンライン所持品へアップロードする機能を作らない。

## 推奨する最初のサーバー構成

ブラウザーの表示は現在のまま維持。Node.jsのサービスが `core.mjs` と `engine.mjs` を共有し、セッションごとの戦闘を60Hz固定stepで進める。クライアントは連番付きの移動入力だけを送り、サーバーが位置・HP・撃破・戦利品を正本として返す。通信方式・配信基盤・ホスティング先は未選定。共有コードが動くことと、負荷・同期・不正耐性が本番水準であることを混同しない。

戦闘サーバーは生成時にシード、コア定義バージョン、編成ハッシュを固定。過大入力、過去連番、同時ログインによる二重探索、加速入力を拒否する。中断・切断の扱いはP2で決め、公開前に説明する。

## 永続データ

accounts / wallets / items / runs / run_rewards / auctions / bid_holds / ledger / idempotency を分ける。アイテムは1現物1UUID、所有者は常に1人。コア番号・能力定義・レア度・能力ごとの個体値はサーバーが発行し固定する。コア以外の装備・素材・消耗品もitemsの共通所有権で管理。

出品中と探索持込中は現物を一時ロックする。永久バインドではなく、二重使用・二重売却を防ぐためのロック。どのアイテム種別にも同じ取引APIを使う。

残高は整数G。DBはbigint、JSON境界では範囲を制限するか文字列で送る。通貨を浮動小数点で扱わない。

## APIの境界

| 操作 | クライアントが送るもの | サーバーが検証・確定するもの |
|---|---|---|
| POST /runs | 基盤の個体ID、段数 | 所有、探索ロック、数字、トップ、合成結果、バージョン |
| run input | 連番、入力方向 | 経過時間、速度、位置、戦闘状態 |
| POST /runs/:id/extract | run ID、冪等キー | 生存、開通、帰還陣への接触、未精算、確定戦利品 |
| POST /auctions | item ID、開始額、任意即決額、期限 | 所有、非ロック、価格、サーバー時刻 |
| POST /auctions/:id/bids | 入札額、冪等キー | 最高額、残高、仮押さえ、旧入札への返金 |
| POST /auctions/:id/buyout | 出品ID、冪等キー | 有効出品、即決額、残高、所有権移転 |
| POST /auctions/:id/cancel | 出品ID | 本人、未落札、入札なし |

リクエストのplayerId、sellerId、所有者は信用せず、認証コンテキストから決める。IDを変更して他人の資産へアクセスできないことをテストする。

## 帰還トランザクション

runをロックし、activeであることと帰還条件を検証。サーバーが保持している未確保報酬だけをitemsへ発行し、残高を加算し、台帳を記録してrunをextractedにする。`unique(run_id,reward_index)` で同じ報酬を二重発行しない。冪等キーも保存し、ネットワーク再送には同じ応答を返す。途中で失敗したら全てロールバックする。

## 即決トランザクション

対象IDを確認後、全ての市場操作で同じ順序（対象item → auction → UUID順のwallet）で行ロックを取得する。ロック後に出品状態・期限・自己購入禁止・所有・残高を再検証。旧入札の仮押さえがあれば返金し、買い手から即決額を減算、売り手に手数料控除後を加算、現物所有者を移し、出品をsoldにする。台帳と冪等応答も同じトランザクションで保存。

PostgreSQLの行ロックとトランザクションを利用する設計。分離レベルと再試行方針を決め、デッドロック・serialization failure時は処理全体を安全に再試行する。参照モデルの逐次テストは、DBでの同時購入検証の代わりにはならない。

期限判定はクライアント時刻ではなく、ロック後のサーバー時刻を使用。入札で確保したGは他の購入に使えない。入札者が自分で即決する場合は確保済み額を精算し二重課金しない。

## 公開前の必須テスト

同じ出品への100並列即決で成功は1件だけ。敗者の残高は不変。同じ帰還を100回再送しても報酬は1回だけ。出品と探索開始を同時実行しても現物はどちらか一方だけがロックする。他人のID指定、期限直前、入札後の即決、切断、DBエラー、処理再試行で総通貨が手数料以外に増減しない。

CSRF対策（Cookie認証の場合）、レート制限、認可、監査ログ、バックアップと復旧、依存ライブラリ監査、秘密鍵の管理を別途実施する。

## 経済の仮方針

手数料5%は現段階の仮値。通貨消費先として修理・加工・探索費等を検討するが、初期装備の欠損で遊べなくなる設計は避ける。全アイテム取引により初期品の複数アカウント供給が起こり得るため、経済モデルを検証してから公開する。能力そのものと数字を市場で検索できるようにし、個体値・期待寄与・未確定報酬を混同させない。
