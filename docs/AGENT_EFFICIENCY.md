# PiXiEED agent efficiency playbook

目的: 品質、操作性、見た目を落とさず、モデル・ツール・検証の重複を減らす。使用率はアカウント全体の共有値であり、個別作業の厳密な課金値ではない。

## 1. 作業開始時の契約

実装前に次の5点を固定する。

1. 今回達成する利用者向けの結果
2. 変更可能なファイル
3. 変更しない機能とデータ
4. 合格条件
5. 今回は確認しない範囲

設計が未確定のまま実装を始めない。方式変更が必要になった場合は、現在の実装を増築せず、一度止めて契約を更新する。

## 2. モデルの使い分け

- SOL: 要件分解、設計判断、範囲管理、統合、最終受入。
- Luna: 境界が明確な実装、棚卸し、機械的変更、純粋テスト。
- Astra: SOLとLunaで解決できない難しい設計、重大なセキュリティ・データ損失リスク、高難度の最終監査だけ。

1つの作業をSOLとLunaで重複実装しない。Lunaの完了後、SOLは差分の重要箇所と受入条件だけを確認する。

## 3. 使用量に応じた運転モード

### 通常モード

週間残量が20%より多い場合。

- 通常の限定委任を利用できる。
- Figmaやブラウザ確認は必要な成果物に限る。
- 全体テストは統合後に1回実施する。

### 節約モード

週間残量が10〜20%の場合。

- 小さな変更はSOLが直接処理し、委任の説明・待機コストを避ける。
- Lunaは複数の密接した修正を1つの縦切りにまとめる場合だけ使用する。
- Figmaは新しい正式資産が必要な場合だけ使用する。
- ブラウザ確認は代表的な1画面と変更経路に限定する。

### 保全モード

週間残量が10%未満の場合。

- 原則として文書更新、読み取り監査、重大不具合の小修正だけを行う。
- Astra、画像生成、広範囲リファクタリング、新規プロトタイプを使わない。
- 緊急でなければ実装候補をMDへ記録し、枠の回復後にまとめて進める。
- テストは変更箇所の限定テストを先に行い、全体テストは公開前または統合単位の最後に1回だけ行う。

## 4. 実装を小さく保つ規則

- 1回の委任は、利用者が確認できる1つの結果に限定する。
- 調査だけの委任と実装の委任を連続させず、読めば分かる範囲は実装担当が同時に確認する。
- 15〜30分相当で結果が出ない場合、範囲拡大ではなく停止・再分割を選ぶ。
- 既存のdirty worktreeを守り、関連しないファイルを整形・削除しない。
- 古い処理を削除する場合は、参照0件、代替経路、回帰テストの3点を証明する。

## 5. 検証回数の上限

原則として、1つの実装スライスで次を上限の目安とする。

| 検証 | 実施タイミング | 目安 |
|---|---|---:|
| 構文・限定テスト | 実装直後 | 1回 |
| 全体ハーネス | 統合完了後 | 1回 |
| ブラウザ確認 | キャッシュ更新後 | 1巡 |
| Figma確認 | 作成直後のメタデータ＋画像 | 各1回 |
| 使用量取得 | 作業開始・終了 | 各1回 |

失敗した場合だけ原因修正後に再実行する。同じ成功確認を根拠なく繰り返さない。

## 6. ブラウザとキャッシュ

- HTML、CSS、ES Moduleの変更をまとめてから版番号を1回更新する。
- 親iframeだけでなく、iframe URLと内部module URLの両方に同じ変更境界を持たせる。
- ブラウザ確認は、表示、主要操作、遷移、コンソールの4点を1巡で確認する。
- PCとスマートフォンで構造が同じ場合は代表2サイズ。構造差がない小修正は代表1サイズでよい。

## 7. Figma利用

- 既存アイコンで意味が一致する場合は再利用する。
- 正式な新規アイコンまたは画面設計が必要な場合だけFigmaを使う。
- アイコンは24px資産と44px以上の操作領域を分離する。
- 作成、検証、書き出しを1セットとして行い、同じ資産を作り直さない。
- 書き出したSVGに背景、不要なstyle、意図しない固定色がないか確認する。

## 8. 作業終了時の報告

必ず次を分ける。

- IMPLEMENTED: 実装済みの利用者向け結果
- UNIMPLEMENTED: 今回対象外または残っているもの
- UNTESTED: 実機、本番、ブラウザなど未確認のもの
- 使用量: 開始値、終了値、差分。枠リセット時は差分を出さない
- 次のステップ: 最も小さい安全な1件

## 9. 現在の知見

- 小規模なUI修正と受入確認は週間枠1〜2ポイント程度の記録が多い。
- 通常の実装、テスト、ブラウザ確認は2〜3ポイント程度が多い。
- Figma作成、実装、全体検証を同時に行う作業は4〜5ポイント程度まで増えた。
- サブエージェントも共有使用量へ含まれるため、委任自体を無料の節約策とは扱わない。
- 5時間枠は途中でリセットされるため、リセットをまたぐ差分を合計しない。
- 最も大きな無駄は、方式未確定のままの実装、キャッシュ不整合、同じ全体テストとブラウザ確認の反復だった。
