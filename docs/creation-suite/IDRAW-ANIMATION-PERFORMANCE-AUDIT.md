## 現行簡単ドットに既にある軽量化

- `pixel-canvas-surface.mjs:9-35`: ImageDataはサイズ変更時だけ再確保。RGBA変換とputImageDataの範囲を変更画素の矩形へ絞る。
- `draw-core.mjs:89-129`: UndoはUint32の画素位置とInt16の前後値。作品全体の画像を各Undoに保持していない。
- `pixel-input.mjs:10-23`: 連続線の画素を線長に応じて生成。全面走査はしない。

これらは維持・共有して使う。「変更範囲描画を新しく導入した」とは報告しない。

## 現行で削減できる仕事

- `draw-page.mjs:337-359`: ストローク開始の全配列コピー。直線プレビューの毎回全配列復元・全面描画。完了時の全面描画。
- `draw-core.mjs:89-97`: Undo差分を作るための全画素比較2回。検証と使用色数の判定も全面走査を重ねる。
- `draw-core.mjs:70-86`: 塗りつぶしごとのキャンバス全体サイズのキュー確保。
- `draw-page.mjs:327-331`: 描き始めごとの使用色Setと色数判定。

128pxから256pxにすると対象画素数は4倍。通常のArrayの実際のメモリ量、Canvas/GPU側の確保量、実機fpsは未測定。

## 初期実装への提案

1. 入力点は欠落させずBresenhamで接続し、画面更新だけをrequestAnimationFrame単位にまとめる。pointerupで未処理点を必ず確定する。
2. 編集中に最初のbefore値と最新after値を記録。Undo作成の全面比較とストローク全体コピーを省く。
3. 直線は前回と次回の変更範囲だけを復元/描画するか、別のプレビュー面に表示する。旧プレビューの残像を検証する。
4. 画素、塗りつぶしキュー、変更位置のbitset、使用色数のカウンターを寸法変更時に確保し直す。通常の編集では再利用する。
5. コマ複製は共有。編集する部分だけ分離する。矩形単位と32pxタイル単位を独立試作で比較する。
6. 再生と表紙を保存状態から分け、コマ切替でPXD全体を保存しない。サムネイル・合成キャッシュは見える範囲を中心に上限を設ける。

小さい疎な絵は切り詰めた矩形が有利になりやすく、全面背景の1画素編集が多数のコマにある場合はタイル単位共有が有利になりやすい。これはコード構造からの推定。試作の画素バイト量と、アプリ接続後の編集時間・保存容量を別々に測って判断する。

## 独立試作の比較結果

`animation-tile-prototype.test.mjs` で、256pxの非反復背景を100コマにした。99複製の各1画素を変更し、元コマを保持。矩形COWの画素payloadは6,553,600バイト、32pxタイルCOWは166,912バイトだった。1編集でプールに追加する画素は最大1,024バイト。空コマは画素なし、16pxキャンバスの端タイルは256バイト。

初期案は32pxタイルで統一する。これにより背景の一部だけが変わるコマで画素を再利用できる。1画素だけの絵では矩形保存の方が小さいため、その透明余白圧縮は保存時の後続候補とする。

`copiedBytes` は新しくプールへ格納するバイト量であり、一時バッファへのコピーを含まない。ここではメタデータ、ヒープ、CPU時間、Canvas/GPU負荷、実機fps、PXDの圧縮後サイズは測定していない。旧iDRAWの速度がそのまま再現できたという結果でもない。

当面採用しないもの: 巨大な旧アプリの一括移植、クラウド共同編集journal、ディスク退避Undo、互換用途の直接RGBA/多色混在モデル、根拠なく追加する描画Worker。依存追加なしで現在の共有Canvasを拡張する。
