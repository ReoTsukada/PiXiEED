# 制作ツールの相互運用・PXD・音楽キャンバス見直し

2026-09-28。現在の作業ツリーと旧 Studio の Git 履歴を読んだ設計レビュー。**この文書は当初の提案記録で、実装完了を示さない。** ユーザー承認後、必要な保存・連携に絞って実装した範囲は [PXD.md](PXD.md) を参照。後続の指示により、音楽は対応色だけを音にし、未割当色も絵として保持する。将来の大きなキャンバス、旧DAW全体、公開方式の変更を今回の実装に含めない。

## 結論

絵の寸法・画素・色と、音符の座標・時間・音色を別の正本として、一つの作品ファイルに収める。PNG経由の再変換を各ツール間の標準経路にしない。PXDには絵、音楽、カメラ出自、パズルの編集データと、それぞれが参照する固定版を格納する。利用期限や公開権限はファイルの内容から付与しない。

画像の保存上限、音楽キャンバスの新規作成上限、再生時の処理量、PNGの出力寸法を別々に管理する。大きい画像を読み込んでも、原本を勝手に縮小・切り取り・減色しない。音楽用の別サイズを作るときはプレビューで確認し、原本と変換条件を保持する。

ここでいう画像の原本は、撮影・描画後のドット画像。未加工のカメラ映像を常時保存する設計ではない。投稿作品の加工利用を他人へ開放する変更も含まない。

## キャンバスとパスの提案

| 対象 | 推奨方針 | 実装・検証の境界 |
| --- | --- | --- |
| 通常の新規作曲 | 現在の16×16を維持 | 現行実装 |
| 拡張の第一段階 | 横128×縦16まで。既存128列の表示不一致を直し、再生を軽量化してから新規拡張を解放 | 提案。128列の内部対応だけでは端末性能の合格を意味しない |
| 拡張の完成目標 | 32×32、64×64、最大128×128を候補にする。横長・縦長も選択できる共通寸法契約にする | 未実装。縦16固定、音程表、4トラック依存の変更と実機検証が必要。上限は負荷試験後に確定 |
| 元の絵の保持 | 少なくとも現在の512×512の論理画素を失わず保存。長方形・RGBA・多色の原本も、音楽サイズと分離して格納 | 現在のDrawバリデーターをそのまま正本に使えない。新しい画像部品と適合層が必要 |
| 保存するPNG | 原寸または整数倍の高解像度出力。PXD内に論理寸法と出力倍率を別に保存 | PNGだけから論理寸法を推測して復元しない |

128×128なら最大16,384セルで、現在の16×16の64倍になる。512×512をそのままリアルタイム作曲上限にすると262,144セルになるため、画像の保管上限をそのまま発音上限にしない。

縦方向を増やすときは、各行の音程を明示したrowPitchMapとその版を保存する。旧16行の音程・PPQ=480・1セル=120 Tickを維持する適合層を置く。行を無制限に増やしてMIDI範囲を超えたり、勝手に音程を折り返したりしない。楽しく聞こえる音域・音階、同音を重ねる場合の音量を試してから上限を決める。

色の保存数と楽器の数を分ける。全画素の色を保持し、複数の色を同じ音色へ割り当てられるようにする。パレットの配列順ではなく安定したcolorIdで結び付け、並べ替え・同じ色の統合で既存音色を変更しない。色を追加した場合の初期音色割当も版付きのルールとして保存する。透明セルは無音、半透明の色は画素のalphaを保ったまま音への対応を定義する。

### サイズ超過・期限切れの扱い

1. 音楽からカメラを開くときは、音楽用の寸法を撮影前に渡す。撮った直後に曲へ戻る体験は維持する。
2. 普通のカメラ画像・絵・PXDを開く場合は先に原本を保持し、現在の作曲上限と照合する。
3. 収まれば、対応する画素座標をそのまま使う。非正方形を引き伸ばして正方形にしない。
4. 通常枠を超える新規作曲なら、拡張を有効にするか、縦横比を保った音楽用コピーをプレビューして選ぶ。広告の自動再生はしない。中止しても原本と編集中の曲を残す。
5. 拡張上限も超える場合は、原本を保ったうえで音楽用コピーを作る。元の絵と同じ大きさの音楽だと表示しない。変換先の寸法・対応座標・減色の有無を記録する。
6. パスが切れたときも、既に作った大きい曲や追加楽器は縮小・削除しない。開く・編集・再生・保存・出力は継続し、新しい領域の拡張や未選択の追加楽器を解放するときだけパスを判定する。
7. パスはファイルに埋め込まない。読み込んだ既存作品を保つ処理と、現在の端末が新しく拡張する権利を分ける。別端末での読み込みや時計の変化も同じルールで試験する。

パスの期限、15分のカメラ要求期限、10分の投稿準備期限は別物。撮影要求が失効したときは、撮影前の曲へ戻って新しい要求を作れる導線にする。

拡張子だけで形式を判断せず、ヘッダーと版で読み分ける。まず旧readerと最小fixtureを切り出し、旧原本bytesを変更せず残す。旧Studio全体やDAWを簡易画面へコピーしない。音楽の持続音、複数レイヤー・フレーム、音声asset、ゲーム状態のように簡易ツールで表せない内容は、別部品として保持し、黙って一枚絵や短い曲へ置き換えない。

新しい共通コンテナは**PXDの新しい版を提案する段階**とする。旧v2に無名の項目を足して互換済みと扱わない。旧アプリは新しい版を読めるとは限らない。必要なら表現可能な部品だけを旧v2へ出す明示的な互換出力を用意し、失う部品を事前に示す。通常保存では新しい共通版を使い、未知部品をそのまま残す。

### 新しい共通ファイルに持つもの

| 部品 | 正本として保持する内容 |
| --- | --- |
| 画像 | assetId、固定revision/hash、幅・高さ、RGBA/透明、colorId付き色、画素、必要な旧レイヤー/フレームと参照。サムネイルは派生出力 |
| カメラ | 撮影後の論理画素、色設定・出自、元の縦横比、保存倍率。現行の一時PNG受け渡しを恒久参照の代わりにしない |
| 音楽 | PPQ、ノートの時刻・長さ・強さ、テンポ・音階、rowPitchMap、colorId→安定したinstrumentId/モデル版、画像の固定版、変換ルール版。音声素材がある作品はそのbytesも保持 |
| 間違い探し | 元/変更後の固定画像版、作者が確定した変更画素の集合・組分け、寸法、問題版。下書きと公開確定を区別 |
| もの探し | 固定画像版、対象の名前・画素マスク、作者の確定状態。表示サイズから正解画素を逆算して保存しない |
| ジグソー | 固定画像版、分割・ピースID・配置・プレイ状態。公開作品は権利の範囲で参照し、他人の投稿を再公開可能な制作素材へ変えない |
| ゲーム・将来の部品 | 自分の素材の固定版と編集状態。理解できない旧部品は実行せず保持。汎用ゲーム制作の実装を現在の完了ゴールへ戻す変更ではない |
| 共通情報 | projectId、部品一覧、形式/部品の版、依存する固定revision/hash、各payloadの長さ・hash、表示用preview。精密GPSやパス期限、認証情報を制作共通ファイルへ自動格納しない |

理解できない部品はbytes・部品ID・hashを保持し、触らずに保存する。既知部品の未知フィールドも型付きの作業用投影だけで再構築しない。対応不能な版は編集を断り、原本を取り出せる。壊れたデータやhash不一致を「未対応」として信頼しない。

「表示＝音楽」の簡易作品では、画像セルとノートを結ぶ座標・固定版を保存する。音楽画面で塗る/消す操作は、対応する画像セルと1セル1音のノートを同じ保存版で更新する。Drawでその作品を開いて対応セルを変更する場合も、保存済みの音色対応・行音程・Tick変換規則を使い、一貫した更新として扱う。二つの部品をそれぞれ最新へ推測して合成しない。旧DAWの持続音やセル外音程など、画像セルと一対一に対応しない曲は別扱いで原曲を保持し、セル曲へ変換するときだけプレビューで確認する。

同じ作品の部品変更は原子的に新しい保存版へ追加する。途中失敗で画像だけ新しくなり曲・問題が古い参照になることを防ぎ、前の保存版を残す。current local-draftsの版付き保存を適合層から利用し、既存下書きを一斉書換えしない。移行成功を検証してから新しい保存先を参照する。ファイルは上限、重複entry、パス、payload長とhashを検査してから読み込む。

## ツール同士の操作

- カメラ→描画：撮影後のドット画像を同じ座標・色のまま開く。高解像度PNGをもう一度縮小してドット寸法を推測しない。
- 絵→音楽：同じ画像を表示してcolorIdごとに音色を対応させる。対応セルの編集は上記の一貫した更新を使う。曲と独立した絵へ置き換えたり、対応しない曲から再生成したりする場合は、手編集の音符を消さず、差分プレビューと適用操作を挟む。独立して編集した曲と画像は、それぞれの版を保持する。
- 音楽→絵：PNG出力と「同じ作品を描画で開く」を分ける。後者では音楽部品を保持し、描画ツールが知らないノートや音色を削除しない。
- 絵→間違い探し：元絵を固定し、Drawで変更後の絵を編集して戻れる入口を用意する。違いは元画素で検出し、作者が統合・分割・除外して確定する。変更後の絵を再編集したら、古い正解を公開確定扱いのままにしない。
- 絵→もの探し：Drawで対象を作り、固定画像上のマスクを問題ツールで指定する。画像のサイズ変更は問題の座標を勝手に引き伸ばさず、新しい問題版で再確認する。
- 地球儀へ公開：制作PXDと公開用画像・問題・OGPを分ける。公開済みの画像を差し替えて既存パズルの正解がずれることを防ぎ、公開作品も固定版へ結び付ける。投稿受付の権限・審査は別ゲート。

PNG/GIFは表示用、WAVは音を聞く出力、MIDIは対応範囲の音符交換、PXDは編集を続ける共通保存と位置付ける。PNGへ戻しただけで元曲の音色やノート長を復元できると説明しない。固定されたノート・音色・モデル版・乱数seedは再現性の条件。現在の合成音にはMath.randomを使う雑音があり、端末間の波形完全一致は保証できない。波形自体を固定したい場合は共通レンダーで生成した音声bytesを保存する。

## 実装順・受入条件

1. **旧PXDの読取と往復基準**：形式識別・v1/v2/Legacy fixture・元bytes保全を追加。画像、音楽、ゲーム、未知entry付きで内容と診断を照合。実ユーザー旧ファイルの確認は別に必要。
2. **共通コンテナと下書き適合層**：画像+曲+未知部品を一つ保存し、Drawで画像だけ編集して音楽と未知部品が一致したまま再保存できるところまで。既存下書きは残す。
3. **Camera/Draw/Audio接続**：logical pixelsとcolorIdを保持。音楽用コピーの確認、原本参照、撮影期限切れ回復を追加。16×16、32×16、128×16、非正方形と多色で検査。
4. **大きい音楽キャンバス**：近い時刻の音符だけを予約し、重なり比較のN²と開始時の全ノード生成を解消。32×32→64×64→128×128の順に端末で測定し、合格した上限だけを公開する。ノートを黙って捨てて軽量化しない。
5. **Drawで問題を編集する往復**：Spot前後版、Hiddenマスク、Jigsaw参照をPXDから再開。DPR・ピンチ・回転・旧版参照・再編集後の確定解除を検査。
6. **公開と保存の最終確認**：共通ファイル、PNG/WAV出力、位置付き公開画像・問題・共有カードの版を照合。実DBや公開変更は別途承認後に行う。

具体的なfixtureと合否は [INTEROPERABILITY-HARNESS.md](INTEROPERABILITY-HARNESS.md) に定義する。第一段階から依存追加なしで実装できる範囲を優先する。ZIP圧縮や新音源ライブラリーが必要になった場合は、必要性とサイズを説明して個別に確認する。
