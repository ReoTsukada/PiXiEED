# 旧投稿を残したまま公開する

## 現在確認できたこと

- 現行の投稿受付は `supabase/functions/create-post/index.ts`、審査・公開は `supabase/functions/moderate-post/index.ts`。公開セルは `post_map_points`、非公開の位置は `post_locations_private`、画像は審査前後で `post-quarantine` と `post-public` に分かれる（`supabase/migrations/20260918102416_user_posting_system.sql`）。
- 当初の `/works/` は旧公式作品の一覧だったが、作品の公開先を地球儀に一本化する方針へ変更した。現行の地図表示は `post_map_points` を件数上限付きで読む。旧 `/works/` は noindex で地球儀へ転送する。
- 作業ツリー上の `20260927062906_classify_globe_posts.sql` は既存行を既定 `pixel_art` とし、新しいカメラ投稿を `pixel_camera` に分ける意図。2026-09-28の本番移行履歴にこの移行はなく、まだ適用されていない。
- 旧 PiXFiND の `pixfind_puzzles` は `origin/pixfind-layout-fix:supabase/migrations/20260310020000_pixfind_puzzles.sql` に定義がある。`client_id` と公開画像 URL で直接操作していた。現在の `auth.uid()` による所有権・審査経路へそのまま接続できない。
- `js/globe/post-store.mjs` のサンプルはメモリ上のデモであり、旧ユーザー作品として数えない。旧データは現行地図投稿とは別の表に残っていた。

上の棚卸し時点から読取専用の実データ確認を進めた結果、`user_posts` と `post_map_points` は **0件**、別系統の `social_posts` は公開 **11件**、`pixfind_puzzles` は **6件**と判明した。`social_posts` の内訳は作品画像1件（`showcase`）、PiXFiND参照6件、Market参照4件。後者10件は元データへの参照であり、別作品として二重に数えない。Marketの公開アセットは6件あり、このうち4件がSNS投稿から参照される。詳しい結果は [確認記録](verification-2026-09-27.md) を参照。

追加の読取確認では、旧SNSの直接画像1件に `creator_user_id` があり、作者本人が元画像のまま場所を選ぶ導線を作れる。PiXFiNDの元・変化後12枚と一覧画像6枚は、ローカル問題画面から実ブラウザーで全件読み込めた。

## 表示の方針

既に公開済みの作品は元のID、公開画像、作成日時、元の公開文脈を変えずに読み取る。作品ギャラリーは地球儀だけとし、明示された場所または場所を持つ店舗との結び付きがある公開作品だけを置く。旧 `social_posts` の `showcase` 画像には公開位置がないため、位置を推測して置かず、元データに残す。PiXFiND参照は問題ページで扱う。`paid` のMarket参照は元の販売・権利条件を保持するが、販売機能を再開するまで公開画面へ出さない。`user_posts` に新しい行ができたら地図・カメラ出自も維持して表示するが、棚卸し時点の本番には0件。旧 PiXFiND は `pixfind_puzzles` の問題ID・slugを保持し、SNS参照と二重掲載しない。`/pixfind/?puzzle=<ID>` と旧 slug の互換入口はローカルで復旧済み。実際に共有されたリンクの全種類は未確認。

公開中だった事実と再利用許可は異なる。公開中の通常投稿画像はジグソーの一時的なプレイだけに使え、保存するのは元投稿の参照・画像指紋・ピース配置であり、公開画像の複製や新しい公開作品を作らない。間違い探し化・音楽化・ゲーム素材化、作品としての派生公開には使わない。既存の `social_posts` 11件はすべて `derivative_allowed=false` だが、ジグソーの遊び以外に加工導線を広げない。旧 `client_id` だけで作者本人を認証しない。`hidden`、`rejected`、`pending` は公開画面に出さず、旧静的サンプルとユーザー投稿を混ぜない。

## 安全な移行順

1. 本番の読み取り専用棚卸し：現行/旧テーブルの有無、状態別件数、Storage 上の画像参照を確認済み。次の実装段階では実際の共有 URL の全種類と画像配信、作者の公開意図を個人情報を記録せず再照合する。ローカル SQL の存在を本番データの存在と取り違えない。
2. 旧行の読取アダプターを作り、未知の状態・壊れた URL は拒否する。実装済みのアダプターは履歴と権利確認に使い、独立した公開一覧は作らない。
3. 地球儀には明示された位置付き公開作品だけを表示する。`user_posts` が増えたら、地図取得上限（`js/app.js` の最大 1000、設定既定 500）でもID・公開状態に欠落がないか確認する。
4. 旧 PiXFiND の公開行と画像実体は閲覧/プレイ用に接続済み。編集や新規公開は現行の本人確認・審査系へ別途設計し、旧クライアント ID を権限として使わない。
5. 本番反映前に件数・URL・権限を実データで照合する。元テーブル、Storage、共有 URL の削除・書換・上書きはこの計画では行わない。

## ハーネス設計

`LEG-01` 旧SNS画像1件を位置なしのまま保持し、PiXFiND参照6件とMarket参照4件を重複した無料画像として数えない。`LEG-02` 非公開状態は地球儀・問題画面に出ない。`LEG-03` 旧 PiXFiND の作者不明行はプレイ可でも改変不可。`LEG-04` 公開位置のない作品は地球儀へ推測配置しない。`LEG-05` 画像欠損、無効な URL、旧スキーマの列欠落で他の作品が消えない。`LEG-06` 地図公開データから精密位置、投稿者 ID、審査前画像に到達できない。`LEG-07` `/pixfind/?puzzle=<ID>` と旧 slug が同じ問題へ着地する。`LEG-08` 将来の `user_posts` は同じ ID・画像・公開セルで地球儀に出る。fixture には公開/非公開/旧列欠落/画像欠損/同一ハッシュ/参照重複を含める。実データの件数照合と URL 到達は本番の読取専用ゲートとして分ける。

**IMPLEMENTED（ローカル）:** 新規地図投稿の受付・審査・地図公開コード、位置なし作品の推測配置拒否、旧 `/works/` の地球儀転送、旧 PiXFiND の閲覧/プレイ入口。旧アカウントで本人のshowcase画像を選び、公開セルだけを保存する画面とRLS移行案もある。旧SNS投稿・PiXFiND問題・画像の本番データは残存。**UNIMPLEMENTED（本番）:** 旧作品の配置テーブル・画面・更新済み投稿受付の公開反映。旧 `client_id` を本人確認には使わない。**UNTESTED:** 実アカウントによる旧作品配置、全旧共有 URL の互換、作者の追加の再利用許可、実機表示、新規投稿から地球儀公開までの本番動作。
