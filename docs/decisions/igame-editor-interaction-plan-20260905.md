# iGAME 操作設計・実装指示 — Astra / 2026-09-05

## 判断と分担

全体把握、調査、システム・画面・操作設計、優先順位、受け入れ判断はAstraが担当する。Lunaは以下の確定仕様を実装する。仕様の選択が必要になった場合はAstraへ戻し、独自に機能や画面を増やさない。

対象は現在チェックアウトに存在する `pixiedraw2/` のデスクトップ版。公開ルートの復活、Bridge、モバイル再設計、依存追加、コミット・公開は対象外。既存の編集内容を保護する。

## 成功の定義

初心者が「描いた素材を選ぶ → 配置する → 動きや音を付ける → 試す → 元の編集へ戻る」を、現在の対象を見失わずに完了できること。パネル数や機能数ではなく、作業の往復、誤操作、保存後の再現性で判断する。

2026-09-05の独立ブラウザー確認では、初期iGAME画面の起動は成功。ただし下部に約60pxの空帯、左の要素ボタンの文字単位の折返し、右の重複見出しがある。ソースでは選択状態の二重管理、通常Playとセル歩行モデルの不一致も確認した。単体テスト成功を製品完成とは扱わない。

## 固定する画面の役割

| 場所 | 役割 | 連動のルール |
| --- | --- | --- |
| 上 | DRAW / GAME / AUDIO、元に戻す、試す・停止 | 制作モードとゲームジャンルを混同しない。ジャンル選択は追加しない |
| 左 | シーン内に配置したものの一覧、表示順、表示・ロック、名前 | 一覧と中央の選択を一致させる。素材の取り込み手順の説明で一覧を押し出さない |
| 下 | 再利用する素材のグリッド。将来は素材・画面UI・ゲーム要素をここへ集約 | クリックは編集対象の選択、ドラッグはシーンへの配置。選択だけで一覧やスクロール位置を飛ばさない |
| 右 | 選択対象の設定を一枚のカードとして表示 | 見出し、選択、設定対象を一つにする。Sprite、移動、当たり判定、重力、動作に対応する音を短い欄で扱う |
| 中央 | グリッド世界の編集と試遊。広さが必要な編集は作業タブ | 素材の詳細編集や範囲選択で広げても、閉じると元のカメラ・選択へ戻る |

レールの位置は安定させる。選択が変わるたびに周囲のパネルを自動で総入れ替えしない。右だけを基本の連動先とし、中央の作業タブはユーザーが詳細を開いた時だけ変える。

## 操作の契約

### 1. 選択と試遊

- シーン、オブジェクト、素材、画面UI、ゲーム要素の選択を単一のworkspace selectionで表現する。
- 画面UIやゲーム要素の過去の選択IDが別のInspectorを優先して表示することを禁止する。
- 試遊中の状態は編集データに書き戻さない。停止時に編集の選択と表示へ戻す。
- 試遊中は設定欄を無効化し、イベント処理側でも編集を防ぐ。
- 既に配置したキャラクターがある場合、その配置・疎な世界・移動設定を通常Playで使用する。別の既定マップへ差し替えない。
- セル移動の歩行アニメーションは一歩ごとに一周。向きと動作からフレームを選び、全オブジェクト共通の再生ヘッドでは駆動しない。

### 2. 素材からキャラクターへ

- Sprite欄そのものを押すとiDRAWで範囲を選択できる。「iDRAWで選ぶ」という別の中継ボタンは増やさない。
- 範囲、使用レイヤー、使用フレーム、セルサイズを一つの取り込み仕様にまとめる。原画を破壊せず参照を保持する。
- 一枚のスプライトシートと複数フレームを同じモーションカードに変換する。レイヤーで分かれたパーツは選択したものを合成して確認できる。
- 動作（待機・歩行・攻撃・ジャンプ）と向きを視覚的に対応付ける。存在しない動作を登録済みとして表示しない。
- 原素材の編集と、シーン内の位置や個別設定を区別する。名前変更で参照が切れないIDを使う。

### 3. 音の配置

- BGM、歩行、ジャンプ、着地、攻撃、タイルを踏むなど、音が使われる欄が入口になる。
- 範囲選択中に「どの対象の、どの動作に入るか」を短い見出しで保持し、決定またはキャンセルで戻る。
- 同じ欄への追加は差し替え。一つの欄に見えない古い割り当てを残さない。外す操作で共有ライブラリの音源そのものは削除しない。
- 選択範囲内の複数トラックの相対時刻を保ち、停止で予約と再生中の音を両方停止する。
- 長さに比例するPCMの一括展開や、全小節分のDOM生成を避ける。表示範囲と再生窓だけを扱う。
- DPCMなどの音色拡張より、通常の音の選択・差し替え・再生・保存の一貫性を優先する。

### 4. マップとゲーム画面UI

- マップの配置単位は常にグリッド。前後関係はレイヤーと深度で扱う。
- 空の世界領域を全生成せず、配置されたセルをチャンク単位で保存する。画面内だけ描画する。「無制限」は作成前の幅高さ入力を不要にする意味であり、有限メモリで文字どおり無限のデータを持つとの約束はしない。
- 画面UIは世界座標と別の画面内基準で配置し、パネル内部はGrid/Flexとスクロールで崩れを防ぐ。
- アイテム表示はゲーム要素のITEMを参照する。素材ライブラリ全体を持ちものとみなさない。
- アイテム効果は対象のステータスIDなどに明示的に結び付ける。表示名の一致や自由文だけで効果先を決めない。

## 表示のルール

- HTMLは操作要素と意味、CSSは配置・余白・状態の見え方、JavaScriptは選択・保存・再生を担当する。
- 暗色、既存のアクセント色、フォーカス表示、既存モーションを維持する。新たな装飾アニメーションは追加しない。
- グリッドの各カードは読める最小幅を確保し、狭い時は列数を減らす。日本語を一文字ずつ縦に折り返して詰め込まない。
- 同じ対象名の見出しを重ねない。説明は必要な空状態・エラー・補助情報に絞り、通常操作の場所を奪わない。
- ドラッグの受け入れ先を示し、無効なドロップは無変更とする。クリック・キーボードによる代替手段も保つ。

## 今回の実装と後続のゲート

1. **着手中**：選択の一元化、通常Playへのセル歩行接続、音の差し替え・解除、空帯・折返し・重複見出しの修正。
2. **次の設計・実装単位**：下部素材棚への集約、Sprite範囲・複数Layer/Frameの実接続、中央の素材編集からの復帰。
3. **次の設計・実装単位**：疎なマップの描画操作と試遊の同一データ化、音の範囲再生、ITEMと効果対象の明示参照。
4. **最終受け入れ**：描画から配置・試遊・保存・再読込を実画面で通す。残った旧コードは参照・互換用途を確認してから別の小さな整理単位で除去する。

この順序は新たな不具合と実操作結果からAstraが更新する。後続ゲートは未完了であり、モデルだけの実装をUIで使える状態と記載しない。

## 並列実装の境界

- Luna（編集動線）：workspace context、workspace UI、対応する選択・接続テスト。
- Luna（表示）：iGAME専用CSSと既存DOM fixtureテスト。共通DRAW/AUDIOレイアウトは変更しない。
- Luna（保存）：音の割り当てモデルと移行・保存テスト。
- 同じ巨大なworkspace UIファイルを複数人が同時に変更しない。実装待ちの間、Astraは実画面検証・次の仕様・差分レビューを行う。

## 受け入れ確認

- ELEMENT → UI_NODE → OBJECT → ASSET → SCENEで右の対象が必ず一致し、下部の選択とカメラが不意に変わらない。
- 配置キャラクターで一歩ずつ歩け、対応フレームが一周し、停止後に編集座標が変わっていない。
- 音Aを設定 → 音Bへ変更 → 外す → 保存・再読込してもA/Bが復活しない。
- デスクトップ1440×900と1024×720で、重なる操作要素、ページ横はみ出し、文字単位の折返しを確認する。
- 型検査、関連単体テスト、DOM接続テスト、実画面操作、保存再読込を別々の検証結果として記録する。

## 調査した原則と採用判断

以下はすべての製品を網羅した調査ではなく、現在の課題に対応する一次資料の比較である。採用方針はAstraの判断。

- [Godot Inspector](https://docs.godotengine.org/en/stable/tutorials/editor/inspector_dock.html)：選択対象のプロパティ表示とプロパティへの素材ドロップ。iGAMEでは露出する設定を少数のカードに絞る。
- [Aseprite Tags](https://www.aseprite.org/docs/tags/)・[Sprite sheets](https://www.aseprite.org/docs/sprite-sheet/)：フレーム範囲の動作単位とシートからの切り出し。描画方式を統一させず、取り込み後の動作カードを共通にする。
- [Tiled Infinite Maps](https://doc.mapeditor.org/en/stable/manual/using-infinite-maps/)：固定サイズを先に決めずに描ける世界。iGAMEでは既存の疎なデータ構造を実際の描画操作にも接続する。
- [Apple HIG Drag and drop](https://developer.apple.com/design/human-interface-guidelines/drag-and-drop)：受け入れ先の反応と代替操作。ドラッグのみでしか作れない操作を避ける。
- [MDN Grid and Flex](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Grid_layout/Relationship_with_other_layout_methods)：二次元のカード棚はGrid、一次元の操作列はFlexを使い分ける。
